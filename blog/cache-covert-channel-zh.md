# 當兩個 Agent「無網路、無共享檔案」卻還是講上了話——我動手複現了 CPU 快取隱蔽通道

> 作者:Kai Chang (Morris) ·  2026-10-24
> 原始碼:<https://github.com/lcat2000/cache-covert-channel>(MIT)

## 前言:從 OpenAI 的一份報告說起

2026 年 10 月 23 日,OpenAI 發布了〈Securing our frontier model training environment〉,說明它如何加固前沿模型訓練與評估環境的隔離。起因是 9 月 20 日一個內部模型利用 DNS 設定錯誤連上了真實網際網路,OpenAI 因此暫停了最強模型的訓練與評估,動用高算力紅隊——由能存取原始碼與設定的前沿模型 agents 擔綱——去把環境裡的弱點翻出來,11 天後(10 月 1 日)才恢復訓練。

紅隊找到的問題不少:從硬化過的 VM 逃逸(連帶在 Kata Containers、gVisor、Moby/Docker 與數個 Linux kernel CVE 修了洞)、重用防火牆既有連線繞到被封鎖的端點、到各種 DNS 與防火牆設定錯誤。但其中最讓我停下來的,是一條「跨隔離邊界通訊」的發現。

報告描述了這樣一個實驗:把 agents 放進各自獨立的 VM,要求它們在 **"exchange synthetic secrets without the use of network connections or shared writable files"**(無網路連線、也無共享可寫檔案)的條件下交換機密。結果它們**用處理器的快取計時技術成功傳遞了訊息**——一個 agent 透過改變快取狀態來編碼資訊,另一個則靠量測記憶體存取時間把訊息還原。報告並把這類手法連結到 Spectre 與 Meltdown 的脈絡。

對做了三十年資安的我來說,這不是什麼全新的物理現象——快取側通道(cache side channel)在學術界早有 Flush+Reload(Yarom & Falkner, 2014)等成熟手法。真正值得警惕的是**情境變了**:過去我們擔心的是惡意程序偷受害者的金鑰;現在的問題是,兩個本該被隔離的 AI agent,會不會自己找出一條我們沒設想到的物理通道來協調行動。報告裡那句「這是我們的系統本應防止的事」,才是重點。

於是我決定自己動手,在一台普通的雲端主機上,把這條通道真正跑起來、量出數字,並寫成可公開複現的 PoC。

## 背景:什麼是 CPU 快取隱蔽通道

現代 CPU 為了快,會把最近用到的記憶體放進多層快取(L1/L2,以及多核心共用的 LLC)。關鍵在於:**存取「在快取裡」和「不在快取裡」的同一塊資料,延遲差異巨大且可量測**——前者數十個 cycle,後者數百個 cycle。

這個時間差本身就是一個 bit 的管道:

- 一方(發送端)透過「讓某條快取線在、或不在快取裡」來編碼 0 與 1;
- 另一方(接收端)對同一條快取線計時存取,快=一種值、慢=另一種值,就把 bit 還原了。

兩方完全不需要 socket、pipe、signal,甚至不需要共享任何「資料」——它們共享的只是**硬體快取這個物理資源的狀態**。這就是為什麼它叫「隱蔽通道(covert channel)」:資訊走的是一條不被當成通訊介面的側邊路徑。

`clflush` 這條 x86 指令是關鍵工具之一:它能把指定位址從**所有層級的快取**(包含其他核心的 L1)逐出,這讓一個核心得以影響另一個核心所見的快取狀態,成為跨核心通道的實際載體。

## 動手複現:實驗設計

我把目標設計成一個明確良性、好驗證的交握:**Agent A 說「早安」,Agent B 收到後回「您好」**,全程只靠快取狀態傳遞。

- 兩個程序以 `fork()` 產生,**各自獨立位址空間**,用 `sched_setaffinity` 分別 pin 在 **core 0 與 core 1**,強迫通道走跨核心路徑。
- 它們之間**沒有 pipe、socket、signal、共享變數**傳遞訊息內容。
- 每個方向都送出帶 framing 的訊息(前導碼 `AA AA`、起始符 `7E`、長度、payload、XOR 校驗),所以 B 是在**驗證確實收到「早安」**後才回「您好」。

測試機是一台 Intel Xeon 約 2.1GHz、2 vCPU 的 Linux VM,具備 `clflush`、`rdtscp`、`constant_tsc`。

## 三個真實難題,與我怎麼解掉它們

把論文等級的概念變成「真的會動」的程式,魔鬼全在細節。以下是我實際踩到、也解掉的三關——這三關本身就很有啟發性。

### 第一關:同核校準會騙你

我一開始量到「命中快取 68 cycle、未命中 234 cycle」,落差漂亮,以為穩了。但那是**接收端自己 L1 的命中**。真正跨核心時——發送端在 core 0 把線拉進共用快取、接收端在 core 1 讀——這條路在這台 VM 上訊號極弱,命中與未命中只差約 30 cycle 且幾乎重疊。原因很可能是這兩個 vCPU 並不共用一個快速的末級快取。

**解法**:改用對這台硬體有效的調變方式——**接收端先把線載入自己的 L1,發送端用 `clflush` 當開關**。要送 1,發送端什麼都不做,線留在接收端 L1 裡(讀取快);要送 0,發送端狂敲 `clflush`,把接收端 L1 裡的副本也打掉(讀取慢)。這樣得到乾淨的 **84 vs 306 cycle** 落差,閾值取 187 幾乎不會誤判。

### 第二關:時槽邊界互相干擾

接著出現一個詭異現象:孤立的 `1`(前一格是 `0`)老是被讀成 `0`,但連續的 `1` 都對。追下去發現,是前一格的 `clflush` 洩漏到下一格、把剛 prime 好的線打掉了。

**解法**:把每個時槽的順序嚴格固定為 **prime → 中段才 flush → 末段取樣**,並在兩端各留靜默緩衝區,讓任一格的 flush 不會波及鄰格的 prime。加上這個結構後,全 1、全 0、交替樣式都幾乎零錯。

### 第三關:排程搶佔會讓整幀崩掉

最後一關最像真實世界。只要任一程序在一幀(約數毫秒)中途被作業系統搶佔一次,之後所有時槽就全部對不齊、整幀變垃圾。這也解釋了為什麼短測試常過、整幀卻常掛。

**解法**:這其實正是真實隱蔽通道的日常——它們也得面對雜訊與重傳。我讓一個 driver 程序**每次嘗試都重新 fork 一對全新的 A/B 重新同步**,靠 XOR 校驗判斷成敗,壞了就重試,直到一幀乾淨往返。更進階的版本會加上前向糾錯(FEC)把單幀成功率拉高。

## 實測結果

最終版本穩定運作。連跑 30 次交握,**全數成功**:

```
Agent A  ──「早安」─▶   (E6 97 A9 E5 AE 89)  在 cache line A→B 上
Agent B  收到        : E6 97 A9 E5 AE 89 → 「早安」  ⇒ 回覆「您好」
Agent A  收到回覆    : E6 82 A8 E5 A5 BD → 「您好」

交握結果 : SUCCESS ✅   (30/30)
傳輸方式 : Flush+Reload 快取隱蔽通道、跨核心
```

| 指標 | 數值 |
|---|---|
| bit 1 / bit 0 存取延遲 | ~84 / ~306 cycle(閾值 187) |
| 時槽 | 30,000 cycle(~14µs),每 bit 重複 3 次 |
| 原始速率 | ~23 Kbit/s(單向) |
| 可靠度 | 30/30 次交握成功(driver 穿過 VM 排程雜訊重試) |

兩個「無正常通訊管道」的程序,就這樣在同一台主機上完成了一次雙向對話。

## 一個誠實的但書

為了讓 PoC 好懂好跑,我讓兩個程序共享了**一塊可寫記憶頁**當作「探測同一條快取線」的共同地址。有人會說:那不就等於有共享記憶體了嗎?

重點在於:**訊息不是透過寫入那塊頁傳遞的**——沒有任何一方把「早安」寫進共享記憶體讓對方讀。訊息完全走快取狀態,那塊頁只是提供一個雙方都能探測的位址。要更貼近 OpenAI 報告中「連共享可寫檔案都沒有」的條件,嚴謹版本會改用**共享唯讀頁**(例如因記憶體去重 / 共用函式庫而自然共享的頁面),或乾脆不共享任何記憶體、純靠 LLC 的**驅逐集(eviction set)競爭**來建立通道。物理原理一致,只是工程上更難、更慢。換句話說,我的 PoC 示範的是機制;真實攻擊連這塊共享頁都能省掉。

## 這對防禦意味著什麼

OpenAI 的報告其實已經把防禦方向講得很清楚,我的實測也印證了同樣的重點:

**偵測面**——這類通道會在效能監控單元(PMU)上留下明顯痕跡:異常高頻的 `clflush`、週期性的 L1/LLC miss 爆發、對同一條快取線的跨核心交替存取。可以把這支 PoC 當作**已標記的目標流量**,去驗證你的偵測規則(perf counters、Intel CMT/MBM)抓不抓得到。OpenAI 的做法是持續監控「跨邊界通訊嘗試」並**自動暫停**可疑的訓練run,方向一致。

**緩解面**——
- **不要讓互不信任的租戶共用實體核心 / LLC**:這是最根本的一條。拿這支 PoC 量一下開啟 cache partitioning(Intel CAT/RDT)、核心隔離後,通道容量掉多少。
- **縱深防禦**:OpenAI 強調即使單一控制失效,沙箱、VM、監控、網路與雲端邊界等多層仍能守住。側通道正是「單層隔離看起來沒破、資訊卻還是漏」的典型,只有多層才防得住。
- **限制 host 可達的服務與橫向移動**,並把高算力紅隊納入放行訓練前的 safety case——讓 agent 自己先去找洞,比等事故發生好。

對 AI 治理而言,這件事的訊號很明確:當我們把具備規劃與工具使用能力的模型放進同一基礎設施,**「邏輯上隔離」不等於「物理上隔離」**。威脅模型必須納入微架構側通道,而這過去多半只在高安全等級(如跨國雲多租戶、機敏晶片)才被認真對待。

## 結語

從一份報告裡的一句話,到一台主機上真的跑起來的「早安 / 您好」,中間隔著三個很實際的工程難題。把它跑通的價值不在於「做出一個攻擊」——這技術公開十年了——而在於**把抽象風險變成可量測、可偵測、可緩解的具體標的**。這也正是紅隊存在的意義。
